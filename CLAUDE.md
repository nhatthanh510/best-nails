# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

Best Nails loyalty app: an iPad **kiosk** (customers type a phone number on a numpad to check in and redeem) and a staff **admin**. The shop is in Hobart: Australian phone numbers, `Australia/Hobart` timezone, `en-AU` formatting.

**Program rules:** exactly 1 point per check-in (not configurable) and at most one check-in per customer per shop day (no cooldown setting; `_award_check_in` checks the calendar day in `settings.timezone`), 10 points = 10% off (a `promotions` row; the type enum only allows `reward`), and a birthday 10% off once per birthday within `birthday_window_days` (7), off until the shop turns it on in Rewards (`birthday_discount_enabled` defaults to false). **One discount per visit:** at most one redemption (points reward or birthday) per customer per shop day, and they don't combine, even with points saved for two (`_discount_used_today`, checked in every redeem function). Customers usually redeem at the till after their service, so a number typed on the kiosk after today's check-in skips the check-in and goes straight to redeeming (`kiosk_today`). There are no multipliers, bonus-points promotions or sign-up bonus; those were removed on purpose, so don't reintroduce them. Printed discount vouchers (% / $ off codes) were removed too, because the shop only uses gift vouchers. **Customer tiers** (New / Regular / VIP) are derived from `lifetime_points` (everything earned: check-ins plus points added by hand) against `settings.tier_regular_points` / `tier_vip_points` (10 / 20) in `lib/tiers.ts`, as in most loyalty programs; `visit_count` stays the factual count of check-ins (history, last visit, reports). **Check-ins only happen on the kiosk** (as in tablet-based loyalty apps; staff can type the number on the iPad for a customer): there is no admin check-in (`admin_check_in` was dropped on purpose). A forgotten visit is made up with Adjust points, which moves the tier but not the visit count, and a mistaken one is taken back the same way: there is no undo for a check-in (`void_check_in` was dropped on purpose; older undone rows keep `voided_at` and are left out of lists and totals). Tiers are not stored, and are admin-only (not shown on the kiosk). **Gift vouchers** are prepaid credit a customer buys (e.g. $100) and spends over several visits. They hold a balance in cents (`gift_vouchers.balance_cents`), and payment still happens at the till. Under Australian Consumer Law they must be valid for at least 3 years, which a check constraint enforces. Admins create, spend, adjust, change the expiry and delete an unspent one. The Claude Design canvas https://claude.ai/artifact/XJjpwCW4RTdw4cEqwgs45Y holds the design: build UI changes in code first, and update the canvas only when the owner asks.

## Commands

Local Supabase runs in Docker, so Docker Desktop must be running.

```bash
npx supabase start        # Postgres + Auth; applies supabase/migrations and supabase/seed.sql
npm run dev               # http://localhost:3000 (/kiosk, /admin)
npm run typecheck && npm run lint && npm run build
npm test                                     # Vitest (lib/**/*.test.ts, app/**/*.test.ts)
npx vitest run lib/phone.test.ts -t "masks"  # single file / single test
npm run test:db           # pgTAP: supabase/tests/*.test.sql (update `select plan(N)` when adding asserts)
npm run test:e2e          # Playwright: e2e/*.spec.ts against the dev server + local Supabase (see docs/AUTOMATED_TESTS.md)
npm run db:reset          # re-run all migrations + seed (also logs everyone out)
npx supabase migration up && npm run db:types   # after adding a migration
```

- **Seed login (local only):** `owner@bestnails.test` / `bestnails-dev`, the one admin. Make staff accounts in the app to test the kiosk-only role.
- **Account management** is in the app (Settings → Accounts, `components/admin/accounts-card.tsx`, `app/admin/account-actions.ts`), never the Supabase dashboard. Admins add accounts with a temporary password (`app_metadata.temp_password`; `requireAdmin` / `requireSignedIn` / the kiosk send them to `/account` to choose their own), edit name and role, reset a password, remove or restore an account, and delete a removed one for good (`deleteAccount`: deletes the auth user, the staff row cascades and history keeps its rows with `created_by` set to null, shown as "Staff"). Removing sets `staff.removed_at` (names stay on history) and bans the sign-in; `getStaff()`, `is_staff()` and `assert_signed_in()` treat a removed account as signed out. The `keep_an_admin` trigger keeps at least one active admin, and nobody changes their own role or removes themselves. `/account` changes your own password (current password required, except on a temporary password or a reset-link session, detected by the `recovery` amr claim). "Forgot password?" (`/admin/login/forgot`) emails a link to `/auth/callback`; it needs SMTP in production (locally the email lands in Mailpit, http://127.0.0.1:54324), and the site's `/auth/callback` URL must be in Supabase Auth's redirect URLs.
- **Accounts:** two roles in `public.staff`: `admin` uses the admin pages and the kiosk; `staff` only the kiosk (sign-in sends them there). The shop has one iPad that staff hand to customers, so there is no device pairing and no rate limit: the kiosk works while any account is signed in on it. Every kiosk step shares one header (`KioskHeader` in `components/kiosk/screens.tsx`, rendered by `kiosk-app.tsx`): the logo on the left; **Gift voucher** (create or use one; linked to the customer once they've typed their number), **Admin** (admin accounts) and **Sign out** (asks first) on the right. A step's own way back is a labelled pill at the top-left of its content, above the heading (`StepBack`), not in the header. Creating, checking and spending gift vouchers are the only admin-side things staff accounts can do: those four functions use `assert_signed_in()` instead of `assert_staff()`, the matching Server Actions use `requireSignedIn()`, and their customer phone lookup runs with the service client because staff can't read `customers`.
- **Migrations** start from one squashed file, `supabase/migrations/20261026000000_initial_schema.sql` (the schema, the settings row and the service menu). There's no reward until the shop adds one on the Rewards page, and the app handles having none. The seed only adds the admin login; there's no test customer data, so make customers on the kiosk.

## Next.js 16 specifics that bite here

- **`cacheComponents` is on.** Anything that reads cookies, the session, `searchParams`/`params` or the DB must sit inside `<Suspense>`. Pages are sync shells that render an async child component. `usePathname()` in a client component also needs a Suspense boundary (see `components/admin/sidebar.tsx` → `nav-links.tsx`).
- **Supabase server code calls `await connection()` first.** `createClient()` and `getKioskDevice()` do this because auth checks read the clock, and `Date.now()` during prerender is a build error.
- **Middleware is `proxy.ts`.** It only refreshes the Supabase session and redirects signed-out `/admin/*` visitors. It's an optimistic check; real authorization happens per action and per read.
- **Mutations refresh the page with `refresh()` from `next/cache`.** To show a message before navigating, actions return `{ ok, message, href }` and the client calls `router.push` (see `createCustomer` and `components/admin/customer-form.tsx`).

## Architecture

**The database owns the points logic** (`supabase/migrations/`). All point changes go through security-definer SQL functions: `_award_check_in`, `kiosk_check_in`, `adjust_points`, `redeem_reward`, `kiosk_redeem`, plus the birthday functions `_birthday_status` / `_redeem_birthday` / `kiosk_redeem_birthday` / `redeem_birthday`.
- **Ledger:** `point_transactions` is append-only and ordered by the `seq` identity, not `created_at`, because rows written in one transaction share a timestamp.
- **Cached totals:** `customers.points_balance`, `lifetime_points`, `visit_count` and `last_visit_at` are protected by the `guard_customer_points` trigger. Only code that sets `best_nails.ledger_write = 'on'` (the functions) can change them. Never update these columns directly from the app.
- **Concurrency:** check-ins and redemptions lock the customer row (`for update`), so double taps can't double-count.
- **Kiosk redemption** requires a check-in within 12 hours (`_checked_in_recently`).
- **Gift vouchers:** the UI says *Create* / *Created* (the app records the voucher; payment happens at the till), while the database keeps the older names (`sell_gift_voucher`, entry kind `sale`, `sold_on`, `sold_by`). `gift_voucher_transactions` is the append-only ledger (`sale` / `spend` / `undo` / `adjust`, ordered by `seq`). `balance_cents` is protected by the `guard_gift_voucher` trigger, the same way as points. All changes go through `sell_gift_voucher`, `spend_gift_voucher` (refuses more than the balance with status `over_balance`; the form offers "Use the full $X · take $Y at the till") and `adjust_gift_voucher`. Spends can't be undone (`void_gift_voucher_spend` was dropped on purpose): a use entered by mistake is put back with Adjust balance and a reason. The `undo` entry kind stays only for older history. `check_gift_voucher` is the read-only preview. Generated codes are the business prefix (`settings.code_prefix`, 2–4 letters, default `BN`; it tells someone with several businesses whose voucher it is) + 7 random digits (`gen_random_bytes`) + a Luhn check digit (`_luhn_check_digit`), e.g. BN48207138: digits only and no hyphens, because staff copy them by hand from paper. Codes are shown exactly as stored. `looksMistyped` in `lib/gift-vouchers.ts` turns a "not found" with a bad check digit into a "looks mistyped" message. The sell form fills in one from `generate_gift_voucher_code` and staff can type over it with a printed number. Codes sold under an older prefix (e.g. GV…) keep working. `gift_voucher_totals` is the unspent credit. The Gift vouchers page is one list (one row per voucher, with its last use: date, amount and customer). Its search matches a code or a customer's name or phone (vouchers they hold or used), and the **Used today** filter is for checking against the till; the full history is on each voucher's page. (A separate Activity view was removed on purpose.)
- **Services & staff:** after Check in (or Join & check in) the kiosk asks "What are you in for today?" (services, many, grouped by category) and then "Who's looking after you?" (one nail technician). Both can be skipped, and a step with nothing turned on is left out. The admin manages them on **Services & staff** (`app/admin/(app)/services/`, `app/admin/service-actions.ts`): add, rename, reorder, hide from the kiosk (`is_active`) or delete. Technicians are the `technicians` table, separate from `public.staff` (sign-in accounts). `kiosk_check_in` takes `p_service_ids` / `p_technician_id` and records them only when the call is the day's check-in: `check_in_services` and `check_ins.technician_name` copy the names, so renaming or deleting never changes history. The menu (from the shop's price list, names only) is inserted at the end of the initial migration; there are no technicians until the shop adds them.
- **Codes:** gift voucher codes are normalised to upper-case alphanumerics (`normalize_voucher_code`) before they're stored or looked up, so typed spaces, dashes and lower case don't matter.
- **Birthdays** are stored as month/day. 29 Feb counts as 28 Feb in other years (`lib/birthday.ts` mirrors this). `birthday_redemptions` is unique per `(customer_id, birthday_year)`.
- **Shop timezone:** "today" and month/year boundaries come from `settings.timezone` via the `shop_day_start(days_ago)` RPC and `shopDate()` in `lib/admin-data.ts`. Never use the server's local `new Date().getMonth()` or similar.
- **Function privileges** are revoked by default. Each new function needs an explicit `grant execute` (`authenticated` for staff functions, which call `assert_staff()`; `service_role` for kiosk functions).

**Two access paths, deliberately different:**
- **Admin** (`app/admin/`, `lib/admin-data.ts`) uses the user-scoped client `lib/supabase/server.ts`, so RLS applies. Only `admin` accounts get in: every read and Server Action starts with `requireAdmin()` (`lib/auth.ts`), which sends staff accounts to the kiosk, and in the database `is_staff()` / `assert_staff()` (kept names) mean "is an admin", so a staff account can't use the admin side even through the API. Any account can read its own `staff` row.
- **Kiosk** (`app/kiosk/actions.ts`) never queries Supabase from the browser. Its Server Actions first call `guard()`, which checks that an account (admin or staff) is signed in. Only then do they use the service-role client `lib/supabase/admin.ts`. There is deliberately no device pairing or rate limit (one shared iPad). Responses carry only first name, masked phone, points, visits and birthday eligibility, because they reach a public screen. Anything exported from a `"use server"` file is a public endpoint, so server-only helpers live in `lib/` (e.g. `lib/kiosk-content.ts`).

**Phone numbers** (`lib/phone.ts`):
- **Storage:** stored as `+<digits>`. An Australian local number loses its leading 0 and becomes `+61…`.
- **Kiosk keypad:** Continue needs at least 10 digits for a number starting with 0 (every AU mobile and landline), 8 otherwise, up to 12 (`isCompleteNumber` in `lib/phone-mask.ts`); longer or unusual numbers show the "not a standard Australian number" warning. The kiosk shows a masked number as "04•• ••• 678" (`maskPhone`).
- **Non-standard numbers are accepted, never blocked.** `normalizePhone()` returns `{ e164, standard }` and the UI warns when `standard` is false.
- **Length:** 8–12 local digits, at most 15 in total (the DB check enforces this too).
- **Client-side formatting:** `lib/phone-mask.ts` (`fillPhoneMask`, `looksStandard`) is kept free of libphonenumber so the kiosk bundle stays small.
- **Admin search:** a search for a local number like `0412` matches stored `61412…`.

**Kiosk UI:**
- **State machine:** `components/kiosk/kiosk-app.tsx` drives the screens in `screens.tsx` (enter → found / signup → services → staff → success / already → redeemed / error).
- **Idle timeout:** clears the number and calls `router.refresh()` to pick up admin changes.
- **Layout:** sized for landscape iPad (1180×820) with a `short:` variant (`@custom-variant short` in `app/globals.css`) for screens ≤780px tall.

**Styling:**
- **Brand:** the logo is a gold butterfly, hand and face profile in a round frame. It's `public/brand/logo-mark.png`, rendered by `BrandMark` in `components/kiosk/brand.tsx` (always shown as a circle), plus `app/icon.png`, `app/apple-icon.png` and the kiosk manifest icons. The palette is ivory, espresso and gold. Logo gold (`--color-gold`) is decorative only, because it's too light for text. Text and buttons use `--primary` (#8a6914), and every text pair passes WCAG AA. Headings (`h1`, wordmark) use Cormorant Garamond (`--font-heading`), and body text uses Plus Jakarta Sans. The kiosk's main buttons use the `bg-gold-sheen` utility; add `disabled:bg-none` when a disabled state swaps the colour.
- **Theme tokens** live in `app/globals.css`. The admin uses shadcn variables, set to the brand palette. The kiosk uses `--color-kiosk-*`. Status colors are `success`, `info` and `warning`.
- **Controls** follow 44px touch targets (`components/ui/button.tsx` and `input.tsx` were resized).
- **Loading states:** page loads use skeletons shaped like the page (`components/admin/skeletons.tsx`, built on `components/ui/skeleton.tsx`) as the `<Suspense>` fallback, never "Loading…" text. An action in progress uses `<Button pending>` (spinner in place of the icon, disabled) or `Spinner` from `components/ui/spinner.tsx`.
- **No `window.confirm`:** use `ConfirmButton` (`components/admin/action-button.tsx`) for destructive actions.

**Migrations:** never edit an applied migration; add a new timestamped file. After changing the schema, regenerate `lib/database.types.ts` (it's generated, so don't hand-edit it). Keep `supabase/seed.sql` and `supabase/tests/loyalty.test.sql` working, since both are run against every migration change.
