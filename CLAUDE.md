# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

Best Nails loyalty app: an iPad **kiosk** (customers type a phone number on a numpad to check in and redeem) and a staff **admin**. The shop is in Hobart: Australian phone numbers, `Australia/Hobart` timezone, `en-AU` formatting.

**Program rules:** exactly 1 point per check-in (not configurable) and at most one check-in per customer per shop day (no cooldown setting; `_award_check_in` checks the calendar day in `settings.timezone`), 10 points = 10% off (a `promotions` row; the type enum only allows `reward`). **Cash reward:** a reward can have amounts instead (`discount_cents` / `cash_discount_cents`): e.g. 7 points, $30 off when at least 7 of the visits since the customer's last points reward were paid in cash, otherwise $10 (`_cash_visits_since_reward`, `_reward_value`; `rewardValueCents` / `cashBonusLine` in `lib/rewards.ts` mirror it). A cash discount alone is a **cash-only reward** (nothing for card): it can't be redeemed until those cash visits are there, so nobody spends points on $0 (`_needs_cash_visits` in both redeem functions, status `cash_visits_required`; `isCashOnly` / `canRedeem` in `lib/rewards.ts`). A discount alone is saved with the same cash amount. A reward is a dollar amount or a percentage (Type `$ off` / `% off` on the form): `discount_percent` / `cash_discount_percent` sit next to the cents columns with the same rules, one kind per reward (`promotions_one_discount_kind_check`), and a redemption records `point_transactions.discount_percent` or `discount_cents`. `rewardAmounts()` in `lib/rewards.ts` reads a row as `{ kind, discount, cashDiscount }`. `saveReward` and the form need at least one of the two; the database still allows neither, only for older rewards named by their title. Every check-in ends with a required "How are you paying today?" step after services/staff (`check_ins.payment_method`, declared by the customer), with or without a cash reward, because the shop records how each visit was paid; the rule line under the heading shows only when an active reward pays more for cash. The kiosk states the rule as information ("$10 off after 7 visits, or $30 off when all 7 are paid in cash", "Higher discount" under Cash, "4 of 7 visits paid in cash") and never tells customers to pay cash; keep it that way. The admin stays light: a Paid column on Check-ins, the dashboard's Today's check-ins and the customer's Points history (shown only when the list has visits the kiosk asked about; on narrow screens it joins the visit line). `VisitPayment` in `components/admin/visit.tsx` draws it: Cash a green pill with a banknote, Card a neutral one with a card icon, so they differ by more than colour, one "visits paid in cash" line on the customer page and a "Count as cash visits" box in Adjust points (both shown whether or not a reward pays more for cash, so the shop's cash numbers stay complete) (`point_transactions.payment_method = 'cash'` on the adjust row), which makes up a forgotten cash visit or, when removing, takes a mistaken one back. There are no per-visit correction buttons (removed on purpose; `set_check_in_payment` exists in SQL but the app doesn't use it). Redeeming spends the points and the cash count starts again; the redemption records `point_transactions.discount_cents`. `redeem_reward` returns jsonb `{points_balance, discount_cents, cash_qualified}`. And a birthday discount once per birthday within `birthday_window_days` (7), off until the shop turns it on in Rewards (`birthday_discount_enabled` defaults to false). It depends on the customer's tier: each tier has `birthday_kind_<tier>` (`percent` or `amount`) and `birthday_value_<tier>` (a percent, or cents; 0 = none for that tier), picked in `_birthday_status`, which returns the customer's `percent` or `amount_cents` (a redemption records the same, exactly one of them). `discountLabel` in `lib/rewards.ts` shows it ("10% off", "$20 off"), and the kiosk advertises `birthdayOffer` ("up to" the best when tiers differ, a plain "birthday discount" when they mix kinds). It needs at least 2 lifetime points (`too_new` below that), so someone who joins on their birthday gets it from their second visit, not the one they join on. In their birthday window the admin shows a Birthday badge (`BirthdayBadge`, from `birthday_badges` via `birthdayBadges()`): a dashed "Birthday soon · claim 10% off" while it can be claimed today, then "✓ Claimed". It's on the Customers list (DoB column) and the customer page, not on check-in lists (Check-ins, the dashboard), where a used one shows as redeemed. **One discount per visit:** at most one redemption (points reward or birthday) per customer per shop day, and they don't combine, even with points saved for two (`_discount_used_today`, checked in every redeem function). Customers usually redeem at the till after their service, so a number typed on the kiosk after today's check-in skips the check-in and goes straight to redeeming (`kiosk_today`, `FoundScreen`, now only for that case). There are no multipliers, bonus-points promotions or sign-up bonus; those were removed on purpose, so don't reintroduce them. Printed discount vouchers (% / $ off codes) were removed too, because the shop only uses gift vouchers. **Customer tiers** (New / Regular / VIP) are derived from `lifetime_points` (everything earned: check-ins plus points added by hand) against `settings.tier_regular_points` / `tier_vip_points` (10 / 20) in `lib/tiers.ts`, as in most loyalty programs; `visit_count` stays the factual count of check-ins (history, last visit, reports). **Check-ins only happen on the kiosk** (as in tablet-based loyalty apps; staff can type the number on the iPad for a customer): there is no admin check-in (`admin_check_in` was dropped on purpose). A forgotten visit is made up with Adjust points, which moves the tier but not the visit count, and a mistaken one is taken back the same way: there is no undo for a check-in (`void_check_in` was dropped on purpose; older undone rows keep `voided_at` and are left out of lists and totals). Tiers are not stored. The kiosk never shows a customer their own tier; it names tiers only in the birthday line on the program card (`birthdayPitch` in `lib/rewards.ts`, e.g. "10% off on your birthday — up to 15% off for VIPs" and "Visit more to reach Regular and VIP for a bigger birthday treat."), to get customers visiting more. **Gift vouchers** are prepaid credit a customer buys (e.g. $100) and spends over several visits. They hold a balance in cents (`gift_vouchers.balance_cents`), and payment still happens at the till. Under Australian Consumer Law they must be valid for at least 3 years, which a check constraint enforces. Admins create, spend, adjust, change the expiry and delete an unspent one. The Claude Design canvas https://claude.ai/artifact/XJjpwCW4RTdw4cEqwgs45Y holds the design: build UI changes in code first, and update the canvas only when the owner asks.

## Commands

Local Supabase runs in Docker, so Docker Desktop must be running.

```bash
npx supabase start        # Postgres + Auth; applies supabase/migrations and supabase/seed.sql
npm run dev               # http://localhost:3000 (/kiosk, /admin)
npm run typecheck && npm run lint && npm run build
npm test                                     # Vitest (lib/**/*.test.ts, app/**/*.test.ts)
npx vitest run lib/phone.test.ts -t "masks"  # single file / single test
npm run test:db           # pgTAP: supabase/tests/*.test.sql (update `select plan(N)` when adding asserts)
npm run test:e2e          # Playwright: e2e/*.spec.ts against the dev server + local Supabase (see docs/AUTOMATED_TESTS.md)
npm run db:reset          # re-run all migrations + seed (also logs everyone out)
npm run db:next-day       # local only: move all visits back a day, so the same customers can check in again
npx supabase migration up && npm run db:types   # after adding a migration
```

- **Seed login (local only):** `owner@bestnails.test` / `bestnails-dev`, the one admin. Make staff accounts in the app to test the kiosk-only role.
- **Account management** is in the app (Settings → Accounts, `components/admin/accounts-card.tsx`, `app/admin/account-actions.ts`), never the Supabase dashboard. Admins add accounts with a temporary password (`app_metadata.temp_password`; `requireAdmin` / `requireSignedIn` / the kiosk send them to `/account` to choose their own), edit name and role, reset a password, remove or restore an account, and delete a removed one for good (`deleteAccount`: deletes the auth user, the staff row cascades and history keeps its rows with `created_by` set to null, shown as "Staff"). Removing sets `staff.removed_at` (names stay on history) and bans the sign-in; `getStaff()`, `is_staff()` and `assert_signed_in()` treat a removed account as signed out. The `keep_an_admin` trigger keeps at least one active admin, and nobody changes their own role or removes themselves. `/account` changes your own password (current password required, except on a temporary password or a reset-link session, detected by the `recovery` amr claim). "Forgot password?" (`/admin/login/forgot`) emails a link to `/auth/callback`; it needs SMTP in production (locally the email lands in Mailpit, http://127.0.0.1:54324), and the site's `/auth/callback` URL must be in Supabase Auth's redirect URLs.
- **Accounts:** two roles in `public.staff`: `admin` uses the admin pages and the kiosk; `staff` only the kiosk (sign-in sends them there). The shop has one iPad that staff hand to customers, so there is no device pairing and no rate limit: the kiosk works while any account is signed in on it. Every kiosk step shares one header (`KioskHeader` in `components/kiosk/screens.tsx`, rendered by `kiosk-app.tsx`): the logo on the left; **Gift voucher** (create or use one; linked to the customer once they've typed their number), **Admin** (admin accounts) and **Sign out** (asks first) on the right. A step's own way back is a labelled pill at the top-left of its content, above the heading (`StepBack`), not in the header. Creating, checking and spending gift vouchers are the only admin-side things staff accounts can do: those four functions use `assert_signed_in()` instead of `assert_staff()`, the matching Server Actions use `requireSignedIn()`, and their customer phone lookup runs with the service client because staff can't read `customers`.
- **Migrations** start from one squashed file, `supabase/migrations/20261026000000_initial_schema.sql`: the whole schema (including gift vouchers, the birthday discount by tier and the cash reward), the settings row and the service menu. It was made with `supabase migration squash`, then the default function lock-down (`alter default privileges ... revoke execute`), the settings row and the menu were added back by hand, because a squash keeps only the schema. Add new migrations after it. There's no reward until the shop adds one on the Rewards page, and the app handles having none. The seed only adds the admin login; there's no test customer data, so make customers on the kiosk.
- **CI and production migrations** (`.github/workflows/ci.yml`): every PR runs typecheck, lint, unit tests and build, plus a fresh Postgres with all migrations applied, pgTAP, and a check that `lib/database.types.ts` is up to date. A push to `main` then runs `supabase db push` against production (secrets `SUPABASE_ACCESS_TOKEN`, `SUPABASE_PROJECT_ID`, `SUPABASE_DB_PASSWORD`; GitHub environment `production`). Production changes only go through that job: never reset or seed it, never change its schema in the dashboard, and never edit, delete or squash a migration once it has reached `main`. The build stays in CI on purpose: a broken build holds the migration back, so the database never gets ahead of the live app.
- **Migrations must be safe in either order.** Vercel deploys the app and the CI job pushes the migration separately, so for a few minutes the old app can run against the new schema or the new app against the old one, and Vercel's Instant Rollback brings back old code without undoing a migration. So every migration must keep the currently live app working: add tables, columns (nullable or with a default) and functions; to change a function's arguments, add the new signature next to the old one. Never rename or drop something live code uses in the same release: add the new thing, switch the app to it, and remove the old one in a later PR, once no deployed code uses it (expand, then contract).

## Next.js 16 specifics that bite here

- **`cacheComponents` is on.** Anything that reads cookies, the session, `searchParams`/`params` or the DB must sit inside `<Suspense>` (or the page exports `instant = false`, see Admin navigation). Pages are sync shells that render an async child component. `usePathname()` in a client component also needs a Suspense boundary (see `components/admin/sidebar.tsx` → `nav-links.tsx`).
- **Supabase server code reads `cookies()` first.** `createClient()` does this because auth checks read the clock, and `Date.now()` during prerender is a build error. Not `connection()`: it isn't allowed inside `"use cache: private"`. **Outside a cache, that isn't enough:** a link prefetch prerenders a page with the cookies available, so `await cookies()` doesn't stop the render, and the session check (or any `new Date()`) then fails with "encountered the unstable value Date.now()". So the components that read the session or the clock outside a cache call `await connection()` first: the admin layout's account blocks, `/account`, the kiosk gate and every `instant = false` page. Reading the clock inside `"use cache: private"` is fine.
- **Admin navigation (no skeletons on a click), with Next's two official options:** pages the kiosk changes (dashboard, customers, check-ins, gift vouchers and their detail pages) export `instant = false` and have no `<Suspense>` of their own, so a click waits for fresh data with the current page still up and the admin's loading line (`NavProgress` in the admin layout: any in-app link tap or `startNavProgress()` starts it, a URL change stops it, and list rows dim meanwhile). Rewards, Services & staff and Settings (only admins change them) cache their data component with `"use cache: private"` + `cacheLife({ stale: 300 })`: at 5 minutes or more the link prefetch carries the data, so they open instantly, and `refresh()` in any Server Action clears it. Adding a `<Suspense>` to a blocking page brings its skeleton back; caching a kiosk-changed page would show visits up to 5 minutes late.
- **Middleware is `proxy.ts`.** It only refreshes the Supabase session and redirects signed-out `/admin/*` visitors. It's an optimistic check; real authorization happens per action and per read.
- **Mutations refresh the page with `refresh()` from `next/cache`.** To show a message before navigating, actions return `{ ok, message, href }` and the client calls `router.push` (see `createCustomer` and `components/admin/customer-form.tsx`).

## Architecture

**The database owns the points logic** (`supabase/migrations/`). All point changes go through security-definer SQL functions: `_award_check_in`, `kiosk_check_in`, `adjust_points`, `redeem_reward`, `kiosk_redeem`, plus the birthday functions `_birthday_status` / `_redeem_birthday` / `kiosk_redeem_birthday` / `redeem_birthday`.
- **Ledger:** `point_transactions` is append-only and ordered by the `seq` identity, not `created_at`, because rows written in one transaction share a timestamp.
- **Cached totals:** `customers.points_balance`, `lifetime_points`, `visit_count` and `last_visit_at` are protected by the `guard_customer_points` trigger. Only code that sets `best_nails.ledger_write = 'on'` (the functions) can change them. Never update these columns directly from the app.
- **Concurrency:** check-ins and redemptions lock the customer row (`for update`), so double taps can't double-count.
- **Kiosk redemption** requires a check-in within 12 hours (`_checked_in_recently`).
- **Gift vouchers:** the UI says *Create* / *Created* (the app records the voucher; payment happens at the till), while the database keeps the older names (`sell_gift_voucher`, entry kind `sale`, `sold_on`, `sold_by`). **One set of words everywhere** (buttons, history, toasts, filters): Create, Activate (a Not sold blank card), Top up, Use, Correct balance; statuses Not sold · Active · Used up · Expired · Blocked, and the list's filter chips use the same names. **Find voucher** (`components/admin/find-voucher.tsx`, `findGiftVoucher`) is the front desk's way in on the Gift vouchers page, the dashboard and the kiosk's Gift voucher menu: type a code, see the voucher, and get only the actions that fit its status (Not sold → Activate; Active → Use / Top up; Used up → Top up; Expired / Blocked → why not; an unknown code that isn't a typo → create one with it). A voucher's page has two columns from `lg`: on the left the balance, the till actions and the printed card; on the right the history, then Details and Admin tools (Correct balance, Block, Delete) folded away. `gift_voucher_transactions` is the append-only ledger (`sale` / `top_up` / `spend` / `undo` / `adjust`, ordered by `seq`). `balance_cents` is protected by the `guard_gift_voucher` trigger, the same way as points. All changes go through `sell_gift_voucher`, `spend_gift_voucher` (refuses more than the balance with status `over_balance`; the form offers "Use the full $X · take $Y at the till") and `adjust_gift_voucher`. Spends can't be undone (`void_gift_voucher_spend` was dropped on purpose): a use entered by mistake is put back with Correct balance (`adjust_gift_voucher`; the voucher page's Admin tools, with Block and Delete) and a reason. It's for mistakes only: money a customer pays for goes on with Top up. The `undo` entry kind stays only for older history. `check_gift_voucher` is the read-only preview. Generated codes are the business prefix (`settings.code_prefix`, 2–4 letters, default `BN`; it tells someone with several businesses whose voucher it is) + 7 random digits (`gen_random_bytes`) + a Luhn check digit (`_luhn_check_digit`), e.g. BN48207138: digits only and no hyphens, because staff copy them by hand from paper. Codes are shown exactly as stored. `looksMistyped` in `lib/gift-vouchers.ts` turns a "not found" with a bad check digit into a "looks mistyped" message. The sell form fills in one from `generate_gift_voucher_code` and staff can type over it with a printed number. Codes sold under an older prefix (e.g. GV…) keep working. `gift_voucher_totals` is the unspent credit. **Printed voucher and self-check:** `VoucherCard` (`components/admin/voucher-card.tsx`) draws the voucher (logo, code, expiry, QR; no amount, since it's spent over several visits and the QR shows what's left). It's a live preview in the create form, and on the Created screen and the voucher's page it has a Print button (a copy goes into `#print-root`, the only thing `@media print` shows). The QR opens the public balance page `/v/<public_token>` (`app/v/[token]/page.tsx`, no sign-in): `gift_vouchers.public_token` is 128 random bits, fixed by `guard_gift_voucher`, because codes are short enough to guess. That page reads only through `public_gift_voucher` (service role; code, amounts, expiry and status, nothing about the customer). The QR's base URL is `NEXT_PUBLIC_SITE_URL`, so set it to the live site before printing vouchers. **Blank cards (Not sold vouchers),** as with Square's physical gift cards: the shop prints cards in advance and activates one when it's sold. **Print blank cards** (a ghost button in the Gift vouchers header from `lg`, and the list's Not sold view; admin; `components/admin/blank-vouchers.tsx`) previews the codes (`preview_gift_voucher_codes`, nothing saved). Save & PDF (saves, then shows the saved cards with Print and Download PDF; nothing downloads until Download PDF is clicked) or Save & print saves them as Not sold vouchers (`create_inactive_gift_vouchers`; status `inactive` in code). A Not sold voucher is a `gift_vouchers` row with no `amount_cents`, `sold_on` or `expires_on` (`gift_vouchers_inactive_check`) and $0. It's tracked in the list under the Not sold filter. Activating it (Find voucher → Activate, the row's ⋯ menu, Activate voucher on its page, or Create gift voucher with its code) sells it with the same code and QR (`sell_gift_voucher` returns `preprinted`); the form's `activate` mode shows the printed code read-only. Until then `check_gift_voucher` and the balance page say `not_sold`, and it can't be adjusted. **Printing and PDF** share one layout: 2 × 5 cards (80 mm, with gaps to cut between) per A4 page, as the `#print-root[data-sheet]` CSS and `SHEET` in `lib/voucher-pdf.ts`. The PDF (for a shop without a printer) captures the on-screen cards with html-to-image into jsPDF, both loaded only on download. A voucher's page has Print, Download PDF and its balance link. The list's checkboxes (`components/admin/bulk-select.tsx`, on rows never used) delete several at once (`deleteGiftVouchers`; RLS keeps any that have been used). **Top up and Block** (as Square and Toast do). Top up (`top_up_gift_voucher`; any signed-in account; from Find voucher or the voucher's page) puts more money on a sold voucher. It's a `top_up` ledger entry and moves the expiry out to at least 3 years from today. `amount_cents` stays the amount at creation, and "Loaded" (`_gift_voucher_loaded`) is sale + top-ups. Block (`block_gift_voucher` / `unblock_gift_voucher`, admin, with a reason) switches off a lost or stolen voucher: `blocked_at` / `blocked_by` / `blocked_reason` on the voucher (not the ledger, whose entries must change the balance). Status `blocked`: nothing can be spent or added, the balance is kept (and still counts as unspent credit), and it's under the Blocked filter. The Gift vouchers page is one list (one row per voucher, with its last use, date and amount, under the code; no Created or Last used columns). Its search matches a code or a customer's name or phone (vouchers they hold or used), the **Used today** toggle (`today=1`, works with any status tab) is for checking against the till, and Sort by orders it (newest, oldest, highest balance, expiring soonest); the full history is on each voucher's page. (A separate Activity view was removed on purpose.)
- **Services & staff:** after Check in (or Join & check in) the kiosk asks "What are you in for today?" (services, many, grouped by category) and then "Who's looking after you?" (one nail technician). Services are required (at least one; Next stays off until then, and there's no Skip), the technician can be skipped, and a step with nothing turned on is left out. The admin manages them on **Services & staff** (`app/admin/(app)/services/`, `app/admin/service-actions.ts`): add, rename, reorder, hide from the kiosk (`is_active`) or delete. Technicians are the `technicians` table, separate from `public.staff` (sign-in accounts). `kiosk_check_in` takes `p_service_ids` / `p_technician_id` and records them only when the call is the day's check-in: `check_in_services` and `check_ins.technician_name` copy the names, so renaming or deleting never changes history. The menu (from the shop's price list, names only) is inserted at the end of the initial migration; there are no technicians until the shop adds them.
- **Codes:** gift voucher codes are normalised to upper-case alphanumerics (`normalize_voucher_code`) before they're stored or looked up, so typed spaces, dashes and lower case don't matter.
- **Birthdays** are stored as month/day. 29 Feb counts as 28 Feb in other years (`lib/birthday.ts` mirrors this). `birthday_redemptions` is unique per `(customer_id, birthday_year)`.
- **Shop timezone:** "today" and month/year boundaries come from `settings.timezone` via the `shop_day_start(days_ago)` RPC and `shopDate()` in `lib/admin-data.ts`. Never use the server's local `new Date().getMonth()` or similar.
- **Function privileges** are revoked by default. Each new function needs an explicit `grant execute` (`authenticated` for staff functions, which call `assert_staff()`; `service_role` for kiosk functions).

**Two access paths, deliberately different:**
- **Admin** (`app/admin/`, `lib/admin-data.ts`) uses the user-scoped client `lib/supabase/server.ts`, so RLS applies. Only `admin` accounts get in: every read and Server Action starts with `requireAdmin()` (`lib/auth.ts`), which sends staff accounts to the kiosk, and in the database `is_staff()` / `assert_staff()` (kept names) mean "is an admin", so a staff account can't use the admin side even through the API. Any account can read its own `staff` row.
- **Kiosk** (`app/kiosk/actions.ts`) never queries Supabase from the browser. Its Server Actions first call `guard()`, which checks that an account (admin or staff) is signed in. Only then do they use the service-role client `lib/supabase/admin.ts`. There is deliberately no device pairing or rate limit (one shared iPad). Responses carry only first name, masked phone, points, visits and birthday eligibility, because they reach a public screen. Anything exported from a `"use server"` file is a public endpoint, so server-only helpers live in `lib/` (e.g. `lib/kiosk-content.ts`).

**Phone numbers** (`lib/phone.ts`):
- **Storage:** stored as `+<digits>`. An Australian local number loses its leading 0 and becomes `+61…`.
- **Kiosk keypad:** Continue needs at least 10 digits for a number starting with 0 (every AU mobile and landline), 8 otherwise, up to 12 (`isCompleteNumber` in `lib/phone-mask.ts`); longer or unusual numbers show the "not a standard Australian number" warning. The kiosk shows a masked number as "04•• ••• 678" (`maskPhone`).
- **Non-standard numbers are accepted, never blocked.** `normalizePhone()` returns `{ e164, standard }` and the UI warns when `standard` is false.
- **Length:** 8–12 local digits, at most 15 in total (the DB check enforces this too).
- **Client-side formatting:** `lib/phone-mask.ts` (`fillPhoneMask`, `looksStandard`) is kept free of libphonenumber so the kiosk bundle stays small.
- **Admin search:** a search for a local number like `0412` matches stored `61412…`.

The Gift vouchers header has Find voucher and a **Create gift voucher ▾ split button** whose menu holds Print blank cards (`CreateVoucherSplitButton`); the Not sold tab has the button too. **Gift vouchers list rows** have a ⋯ menu (`components/admin/voucher-row-actions.tsx`): the actions that fit the status (Use, Top up, Create), Copy code / balance link, Print, and Block / Unblock / Delete, with the forms in a dialog over the list. Large screens add Amount and Expires columns. **Dialogs** (`components/ui/dialog.tsx`) are centred cards at every size. Headings in the serif font use lining figures (`h1, .font-heading` in `globals.css`), or codes read "BNoo…". **Gift vouchers list layout** (`components/admin/list-layout.tsx`): the title with the page's buttons, a `SummaryCard` of a few numbers, `StatusTabs` with counts (one per status; the counts aren't narrowed by a search, `giftVoucherCounts`), then the `ListPanel` with search, the Used today switch (`FilterSwitch`) and Sort by above the rows. Only for statuses, where every voucher is in exactly one tab: Customers' visit filters overlap and Check-ins picks a date range, so those keep chips / the joined range bar and a one-line subtitle.

**Kiosk UI:**
- **State machine:** `components/kiosk/kiosk-app.tsx` drives the screens in `screens.tsx` (enter → services (a returning customer not yet checked in today goes straight here: the first step greets them, "Welcome back, Nathan · 04•• ••• 888", with "Not you? Start over"; there's no Welcome back → Check in tap, as in Galaxy-style kiosks) / signup → services → staff → payment (always the last step; tapping Cash or Card checks in) → success, which lists the services, technician and payment back / already → redeemed / error). Services and staff were tried on one two-column screen and the owner preferred separate screens, so keep them apart..
- **Sign-up name:** the kiosk asks for one name ("Your name", "What should we call you?"), as check-in kiosks do (Galaxy; Square Loyalty asks for none). `signupSchema` in `app/kiosk/actions.ts` stores the first word as `first_name` (the only part the kiosk shows) and the rest as `last_name`; the admin keeps both fields so staff can tidy names up. Don't add a Last name field back to the kiosk.
- **Idle timeout:** clears the number and calls `router.refresh()` to pick up admin changes.
- **Errors and warnings:** an error uses `KioskError` (`--color-kiosk-error` with an icon; the same red as `--destructive` in the kiosk's Gift voucher dialog), and an invalid field gets the red edge from `aria-invalid`. Kiosk fields (`fieldClass` in `screens.tsx`) have the admin inputs' three states in kiosk colours: a resting edge at 3:1, a softened gold edge plus a faint halo on focus, and a red edge and halo when invalid. `kiosk-notice` (peach, with a triangle) is only for warnings such as a non-standard number. Sign-up fields share one look (bold label, then the field). The exception is the birthday: while the birthday discount is on it sits in a gold-edged card ("Add your birthday for a special birthday treat" / "Optional · a little treat could be waiting for you around your birthday."), otherwise it's a plain field. That copy names no amount and promises nothing on purpose: a big number tempts people to give a birthday that's coming up, and not every tier or first visit gets one.
- **Layout:** sized for landscape iPad (1180×820) with a `short:` variant (`@custom-variant short` in `app/globals.css`) for screens ≤780px tall.
- **Collapsible sidebar:** from `lg` the owner can collapse the admin sidebar to the icon rail with the panel button beside the logo or ⌘\ / Ctrl+\ (`components/admin/sidebar-toggle.tsx`; the width animates; collapsed (`lg:rail:`), the button is the small logo in the same row, showing the expand icon on hover, so nothing below moves; remembered in localStorage and restored before paint by `RESTORE_SIDEBAR` in `lib/sidebar.ts`, which sets `data-nav-collapsed` on `<html>`). The `rail:` variant (`app/globals.css`) styles the rail both on tablets and when collapsed, so use it, not `md:max-lg:`, for rail styles.
- **Admin `wide` / `below-wide` variants** (`app/globals.css`, 1140 px): where the admin content area has room for a list's extra columns or a page's second column. An iPad in landscape (1024 px) has the full sidebar and is below it; the 1180 px kiosk iPad is above. The Gift vouchers list uses them, rather than `lg`; a voucher's page has two columns from `lg`.

**Styling:**
- **Brand:** the logo is a gold butterfly, hand and face profile in a round frame. It's `public/brand/logo-mark.png`, rendered by `BrandMark` in `components/kiosk/brand.tsx` (always shown as a circle), plus `app/icon.png`, `app/apple-icon.png` and the kiosk manifest icons. The palette is ivory, espresso and gold. Logo gold (`--color-gold`) is decorative only, because it's too light for text. Text and buttons use `--primary` (#8a6914), and every text pair passes WCAG AA. Headings (`h1`, wordmark) use Cormorant Garamond (`--font-heading`), and body text uses Plus Jakarta Sans. The kiosk's main buttons use the `bg-gold-sheen` utility; add `disabled:bg-none` when a disabled state swaps the colour.
- **Theme tokens** live in `app/globals.css`. The admin uses shadcn variables, set to the brand palette. The kiosk uses `--color-kiosk-*`. Status colors are `success`, `info` and `warning`.
- **Controls** follow 44px touch targets (`components/ui/button.tsx` and `input.tsx` were resized).
- **Dropdowns** are native `<select>`s (the iPad's picker wheel on the kiosk) with one chevron drawn by an unlayered rule at the end of `app/globals.css` (`--select-chevron`, a lighter one under `[data-kiosk]` / `.kiosk-theme`). Don't add per-component arrow icons.
- **Loading states:** page loads use skeletons shaped like the page (`components/admin/skeletons.tsx`, built on `components/ui/skeleton.tsx`) as the `<Suspense>` fallback, never "Loading…" text. An action in progress uses `<Button pending>` (spinner in place of the icon, disabled) or `Spinner` from `components/ui/spinner.tsx`.
- **No `window.confirm`:** use `ConfirmButton` (`components/admin/action-button.tsx`) for destructive actions.

**Migrations:** never edit an applied migration; add a new timestamped file. After changing the schema, regenerate `lib/database.types.ts` (it's generated, so don't hand-edit it). Keep `supabase/seed.sql` and `supabase/tests/loyalty.test.sql` working, since both are run against every migration change.
